## 1. 背景与目标

校招/秋招场景下，求职者的时间被三类重复劳动吞噬：**重复填网申表单**、**跨平台跟踪投递进度**、**信息搜集与刷题缺乏闭环**。

OfferConsole 的定位是**个人求职操作系统**：以浏览器插件为执行终端、本地数据为准、飞书多维表格为总库视图、LLM 为筛选与生成引擎，分三个阶段实现：

- **P0 省时间**（M1/M2）：简历库 + 网申自动填 + 投递进度管理，先把重复劳动砍掉
- **P1 提效率**（M3）：批量渠道、信息聚合、岗位匹配、简历多版本，先筛后投
- **P2 智能闭环**（M4）：学习计划、渠道效能、模拟面试、数据仪表盘

**非目标**：不做机考/正式面试 AI 代答；不做官网全自动提交（验证码不可行）；不做面向他人的 SaaS。

## 3. 关键设计决策

### D1 基座选型：fork Job-ApplyMate（已验证，2026-09-22）

两个候选基座实测对比，Job-ApplyMate 全面胜出，详细对比见附录 A。核心理由：

1. 功能与 P0 几乎 1:1 重合（多简历库 / 逻辑表单识别 / 失败学习 / 投递记录 / WebDAV 均已内置）
2. 纯插件无原生依赖（无 nativeMessaging），本地优先
3. TS + Vite + React 工程化，核心逻辑有 node:test 单测覆盖
4. AI 隐私设计理念一致（简历原文不随扫描请求外发）
5. MIT 协议，允许 fork

> 风险提示：上游为 2026-08 新建的单人项目（28 star），须 pin 版本 fork，不跟随上游主线滚动升级；上游更新经评审后 cherry-pick。

### D2 投递进度：本地为准，单向推送飞书

放弃"与总表双向同步"。双向同步的冲突处理与飞书 API 限流是复杂度高估点。

- 插件本地（chrome.storage + IndexedDB）为唯一事实源
- 每次投递记录变更后，经消息队列式重试推送至飞书多维表格（写失败进入本地待重试队列）
- 飞书侧仅作视图与筛选，不回写；如确需回写（如标记 offer 状态），M3 再评审

### D3 Boss 渠道：半自动，不全自动

get_jobs 类脚本多为逆向接口，拟人化节奏不能消除封号风险。降级为半自动：

- 脚本职责：JD 列表抓取、去重、打招呼语 LLM 生成、投递清单整理
- 人工职责：浏览清单并亲自点击投递
- 收益保留约 80%，账号风险降一个数量级

### D4 秋招信息聚合：结构化源优先，不爬公众号

公众号爬取合规风险高且维护成本大。信息源优先级：

1. 牛客校招日程、Offershow 等现成聚合页（人工/RSS 订阅）
2. 目标公司官网招聘页（允许 robots 的范围内低频抓取）
3. 人工补漏录入

统一进入"截止提醒"数据表，cron + 系统通知/邮件提醒。

### D5 底线补充 L4：LLM 调用前 PII 脱敏

简历含姓名、电话、身份证等敏感信息。所有发往 LLM（OpenAI 兼容 API：DeepSeek/豆包/通义）的请求：

- 默认走脱敏层（参考 Resume Pro 的 `redact` 思路：姓名→占位符、电话/邮箱/身份证→掩码）
- 需要原文的场景（如 AI 简历重组）必须显式用户确认
- API Key 仅存本地，不进入备份导出文件以外的任何远端

## 4. P0 功能详述

### 4.1 简历库 + 一键导入

- **用户故事**：作为求职者，我从超级简历导出 PDF，导入插件后自动解析出结构化资料，多份简历按求职方向分类管理。
- **复用**：Job-ApplyMate 多简历库 + pdfjs-dist / mammoth / marked 解析管线。
- **验收标准**：
  - PDF/DOCX/MD 导入后，基本信息、教育经历、实习/项目经历解析准确率 ≥ 90%（以人工校对抽样 20 份为准）
  - 多简历独立保存解析资料，切换简历后自动填与文件上传同步切换
  - 解析失败 45s 超时回退本地规则，不卡死界面

### 4.2 官网网申自动填

- **用户故事**：打开目标公司官网网申页，一键填充已保存资料；未识别字段通过问答补填并记住，下次自动复用。
- **复用**：Job-ApplyMate 逻辑表单识别（单选组/复选组/日期拆分/经历块绑定）、下拉框增强、失败学习（learnedFields + AI 纠错 Skill）、AI 扫描填充、信息浮窗兜底。
- **自建**：目标公司站点实测清单（M1 先覆盖 3 家：腾讯/阿里/字节官网），记录每家字段识别成功率与特殊控件。
- **验收标准**：
  - 3 家目标站点常规字段（基本信息+教育经历）填充成功率 ≥ 85%
  - 失败字段可问答补填，答案写入个人资料 + 站点学习记录
  - **提交动作永远由人完成**，插件不提供自动提交开关

### 4.3 投递进度管理

- **用户故事**：每完成一次网申，插件自动/半自动生成投递记录；飞书总表实时可见全部进度。
- **复用**：Job-ApplyMate 投递记录模块（新建/筛选/排序/CSV）。
- **自建**：飞书多维表格写入适配器（App Token 本地配置、失败重试队列）。
- **验收标准**：
  - 投递记录字段与飞书总表 schema 对齐（公司/岗位/渠道/投递时间/阶段/状态/面经链接）
  - 本地变更后 5s 内推送飞书，失败进入重试队列并在插件内可见

### 4.4 笔试刷题打卡

- **用户故事**：每天刷题后在插件里一键打卡，记录题目来源（牛客/CodeTop）、题号、标签、耗时。
- **自建**：打卡面板 + 本地统计（连续天数、标签分布）。
- **验收标准**：打卡数据进入本地存储与备份文件；可导出 CSV。

### 4.5 数据备份 / 隐私

- **复用**：Job-ApplyMate JSON 版本化备份 + WebDAV ETag 同步（412 冲突保护、凭据不上远端）。
- **验收标准**：备份往返不丢字段；WebDAV 冲突时明确提示而非静默覆盖；备份文件明文风险提示文案保留。

## 5. 数据模型（本地为准）

| 实体 | 关键字段 | 存储 |
| --- | --- | --- |
| Profile（个人资料） | 基本信息、教育经历[]、实习经历[]、项目经历[]、技能、证书、自定义字段[] | chrome.storage |
| Resume（简历） | 文件 Blob、原文件名、分类标签、解析资料快照 | IndexedDB |
| ApplicationRecord（投递记录） | 公司、岗位、渠道、投递时间、阶段、状态、JD 链接、面经链接、飞书行 ID | chrome.storage + 飞书镜像 |
| LearnedField（学习记录） | 站点、字段签名、答案来源、AI 纠错规则 | chrome.storage |
| SiteAdapter（站点适配） | 站点域名、字段映射覆盖、兼容性备注 | chrome.storage |
| StudyCheckIn（刷题打卡） | 日期、来源、题号、标签、耗时 | chrome.storage |

## 6. 技术架构

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 浏览器插件 | TS + Manifest V3 + React 19 + antd 6 + Vite（fork Job-ApplyMate） | 执行终端：表单识别/填充、简历库、投递记录 |
| 本地存储 | chrome.storage（结构化）+ IndexedDB（文件） | 唯一事实源 |
| 备份 | JSON 导出 + WebDAV（ETag） | 跨设备与容灾 |
| 总库视图 | 飞书多维表格 | 单向写入，只读视图 |
| Agent 层（M3+） | Python/Node 脚本 + cron | Boss 半自动、信息聚合、截止提醒 |
| LLM | OpenAI 兼容 API（DeepSeek/豆包/通义） | 前置 PII 脱敏层（L4） |

---

## 7. 边界与合规（四条底线）

- **L1** 官网不做全自动提交：验证码不可逾越，永远"自动填 + 人工点提交"
- **L2** Boss/实习僧渠道不裸奔：半自动 + 拟人化节奏，禁止并发批量请求
- **L3** 机考/正式面试不碰 AI 代答
- **L4** LLM 调用前 PII 脱敏，需原文时显式用户确认
